# ADR-001: Server-only, versioned Supabase phrase persistence

Date: 2026-10-12

Status: Accepted

## Context

Every player needs the latest shared phrase list, while administrative updates
must persist without overwriting a concurrent editor's work. No player state
belongs in the database. Login-rate-limit storage must work across app instances
without retaining raw client addresses or an unbounded history of attempts.

## Decision

Use a singleton Postgres row with a checked `id = 1`, a positive integer version,
validated phrase array, and a database-generated timestamp. Supabase is accessed
only through a `server-only` service-role client. Enable RLS and revoke table and
function access from `PUBLIC`, `anon`, and `authenticated`; no public policies
are installed. The public Next.js route exposes only the validated version and
phrases and marks success and error responses `no-store`.

Updates use a security-invoker RPC containing one `UPDATE ... WHERE version =
expected_version RETURNING ...`. Postgres handles locking and version checks
atomically. Zero returned rows means a conflict; there is no read-then-write
window. Seeding uses `INSERT ... ON CONFLICT DO NOTHING`, so initialization
cannot replace an existing configuration even during simultaneous seed runs.
Database functions have an empty search path and explicit execution grants.

Runtime validation rejects malformed database responses. Repository errors
distinguish missing configuration, invalid data, unavailable storage, and stale
writes without copying database or network diagnostics into public responses.
No bundled fallback phrases are served on errors. Disable SDK retries and bound
database requests to ten seconds so callers control retry behavior.

Store one capped failure counter per keyed client hash with a maximum 15-minute
expiry, not one row per attempt. A Supabase Cron job purges expired identifiers
every minute. The phase 5 implementation must use HMAC-SHA256 with a server secret
and treat expired records as inactive even before physical cleanup. Overall row
count scales with distinct clients in the active window; this is not a global
fixed-capacity limiter. Monitor Cron and storage as part of deployment operations.

## Consequences

The public shell and build do not need credentials. The phrase API requires a
migrated and seeded database. Applying migrations and seeding a live project are
operator tasks. Cron availability and its scheduled job must be verified on the
target project. PGlite tests execute the core SQL and permissions locally;
mocked SDK HTTP tests cover the application boundary. Hosted PostgREST behavior,
multi-connection concurrency, and the Cron scheduler still require deployment
smoke checks. Phase 5 adds authentication and rate-limit operations; phase 6 maps
repository conflicts to HTTP 409 in the protected editor API.
